# 메시징 기술 비교: SyncML vs MQTT vs RabbitMQ vs Kafka

> 이 문서는 프로젝트에서 사용하거나 비교 대상이 되는 메시징/프로토콜 기술을 정리한다.

---

## 0. 핵심 결론: MQTT, RabbitMQ, Kafka는 본질적으로 같다

**셋 다 하는 일:**
```
"야, 이거 있어" → Consumer에게 전달
```

**비유:**
```
셋 다 "택배 배송"

MQTT     = 오토바이 퀵서비스 (빠르고 가볍고, 외부 배송)
RabbitMQ = 일반 택배 (내부 물류센터 간 배송)
Kafka    = 대형 물류창고 (대량 배송 + 보관 + 재확인 가능)
```

**차이는 프로토콜 + 부가기능:**

| 항목 | MQTT | RabbitMQ | Kafka |
|------|------|----------|-------|
| **본질** | 알림 전달 | 알림 전달 | 알림 전달 |
| **대상** | 외부 IoT | 내부 서비스 | 내부 서비스 (대용량) |
| **프로토콜** | 경량 (2B 헤더) | AMQP (무거움) | 자체 프로토콜 |
| **메시지 보관** | 일부 (Retained) | ❌ 소비 후 삭제 | ✅ 영구 저장 |
| **재처리** | ❌ | ❌ | ✅ offset 이동 |
| **처리량** | 중간 | 중간 | 매우 높음 (수백만/sec) |
| **부가기능** | QoS, Last Will | Exchange 라우팅 | 파티션, 컨슈머 그룹 |

**선택 기준:**
```
외부 IoT 통신        → MQTT
내부 단순 작업 분배   → RabbitMQ
대용량 + 로그 + 분석  → Kafka
```

> **결론**: 본질은 같은 "메시지 전달". 환경/규모/부가기능에 따라 프로토콜이 다를 뿐.

---

## 1. 한눈에 비교

| 기술 | 역할 | 통신 대상 | 데이터 형식 | 특징 |
|------|------|----------|------------|------|
| **SyncML** | 외부 통신 프로토콜 | 단말 ↔ 서버 | XML | OMA 표준, 상태 기반 |
| **MQTT** | 외부 통신 프로토콜 | 단말 ↔ 브로커 ↔ 서버 | 자유 (주로 JSON) | IoT 표준, 경량, Pub/Sub |
| **RabbitMQ** | 내부 메시지 브로커 | 서버 ↔ 서버 | 자유 (JSON, 바이너리) | 범용 큐, 라우팅 강력 |
| **Kafka** | 내부 이벤트 스트리밍 | 서버 ↔ 서버 | 자유 (JSON, Avro) | 대용량 로그, 순서 보장 |

## 2. SyncML vs MQTT 상세 비교

둘 다 **"단말과 서버 간 통신 프로토콜"**이지만 설계 철학이 다르다.

### 2.1 기본 정보

| 항목 | SyncML (OMA-DM) | MQTT |
|------|-----------------|------|
| **정식 명칭** | Synchronization Markup Language | Message Queuing Telemetry Transport |
| **표준 기관** | OMA (Open Mobile Alliance) | OASIS / ISO |
| **탄생 배경** | 2000년대 모바일 기기 동기화 | 1999년 IBM, 저전력 IoT 센서 |
| **주요 사용처** | 차량 OTA, 통신사 MDM | IoT, 스마트홈, 신형 차량 |
| **현재 트렌드** | 레거시/표준 필수 환경 | **현재 대세** |

### 2.2 통신 구조 비교

```
┌─────────────────────────────────────────────────────────────────┐
│                        SyncML 구조                               │
├─────────────────────────────────────────────────────────────────┤
│                                                                 │
│   [단말] ◄───────── HTTP 요청/응답 ──────────► [서버]           │
│                                                                 │
│   • 단말이 먼저 접속 (Polling)                                   │
│   • 요청-응답 구조 (Request-Response)                            │
│   • 서버가 단말에 먼저 연락 불가                                  │
│   • 연결 유지 안 함 (Stateless HTTP)                             │
│                                                                 │
└─────────────────────────────────────────────────────────────────┘

┌─────────────────────────────────────────────────────────────────┐
│                        MQTT 구조                                 │
├─────────────────────────────────────────────────────────────────┤
│                                                                 │
│   [단말] ◄───── 지속 연결 (TCP) ─────► [MQTT Broker] ◄──► [서버]│
│                                                                 │
│   • 단말이 브로커에 연결 유지                                     │
│   • Pub/Sub 구조 (발행/구독)                                     │
│   • 서버가 단말에 즉시 Push 가능                                  │
│   • 연결 유지 (Persistent Connection)                            │
│                                                                 │
└─────────────────────────────────────────────────────────────────┘
```

### 2.3 데이터 형식 비교

**SyncML (XML, 무거움)**
```xml
<?xml version="1.0" encoding="UTF-8"?>
<SyncML xmlns="SYNCML:SYNCML1.2">
  <SyncHdr>
    <VerDTD>1.2</VerDTD>
    <VerProto>DM/1.2</VerProto>
    <SessionID>abc123</SessionID>
    <MsgID>1</MsgID>
    <Target><LocURI>http://server/syncml</LocURI></Target>
    <Source><LocURI>IMEI:123456789</LocURI></Source>
    <Cred>
      <Meta><Type>syncml:auth-basic</Type></Meta>
      <Data>dXNlcjpwYXNz</Data>
    </Cred>
  </SyncHdr>
  <SyncBody>
    <Alert>
      <CmdID>1</CmdID>
      <Data>1201</Data>
    </Alert>
    <Final/>
  </SyncBody>
</SyncML>
```
→ **약 500 bytes**

**MQTT + JSON (경량)**
```json
{
  "type": "ALERT",
  "code": 1201,
  "vin": "VIN-0002",
  "timestamp": "2026-03-31T14:00:00Z"
}
```
→ **약 80 bytes** (6배 가벼움)

### 2.4 기능 비교

| 기능 | SyncML | MQTT |
|------|--------|------|
| **서버 → 단말 Push** | ❌ 불가 (단말이 먼저 접속해야) | ✅ 즉시 가능 |
| **연결 유지** | ❌ 매 요청마다 새 연결 | ✅ 지속 연결 |
| **QoS (전달 보장)** | 없음 (HTTP 기반) | 0, 1, 2 레벨 지원 |
| **오프라인 메시지** | ❌ | ✅ Retained Message |
| **Last Will (유언)** | ❌ | ✅ 연결 끊김 시 자동 알림 |
| **인증** | Cred (Basic, MD5) | Username/Password, TLS |
| **데이터 형식** | XML (고정) | 자유 (JSON, 바이너리 등) |
| **대역폭** | 높음 (XML 오버헤드) | 낮음 (최소 2바이트 헤더) |

### 2.5 언제 뭘 쓰나?

| 상황 | 추천 |
|------|------|
| **표준 준수 필수** (자동차 OEM, 통신사) | SyncML |
| **레거시 시스템 연동** | SyncML |
| **신규 IoT 프로젝트** | MQTT |
| **실시간 Push 필요** | MQTT |
| **저전력/저대역폭** | MQTT |
| **양방향 즉시 통신** | MQTT |

### 2.6 MQTT Pub/Sub 개념

MQTT는 **발행/구독(Publish/Subscribe)** 모델이다.

```
┌─────────────────────────────────────────────────────────────────┐
│                      MQTT Pub/Sub 구조                           │
├─────────────────────────────────────────────────────────────────┤
│                                                                 │
│   [서버]                                                        │
│     │                                                           │
│     │  Publish                                                  │
│     │  Topic: vehicle/VIN-0002/commands                         │
│     │  Message: {"type":"OTA_AVAILABLE",...}                    │
│     ▼                                                           │
│   ┌─────────────────────────────────┐                          │
│   │         MQTT Broker             │                          │
│   │   (Mosquitto, HiveMQ 등)        │                          │
│   └───────────────┬─────────────────┘                          │
│                   │                                             │
│         ┌─────────┼─────────┐                                  │
│         │         │         │                                   │
│         ▼         ▼         ▼                                   │
│   [VIN-0001]  [VIN-0002]  [VIN-0003]                           │
│   (구독 안함)  (구독 중)   (구독 안함)                            │
│               ↓                                                 │
│        메시지 수신!                                              │
│                                                                 │
└─────────────────────────────────────────────────────────────────┘
```

**Topic 예시:**
- `vehicle/VIN-0002/commands` - 특정 VIN에 명령
- `vehicle/+/status` - 모든 VIN의 상태 (와일드카드)
- `vehicle/#` - vehicle 하위 모든 토픽

### 2.7 SyncML vs MQTT 시퀀스 비교

**SyncML: 단말이 먼저 물어봐야 함**
```
[단말]                              [서버]
   │                                   │
   │  (5초마다 Polling)                │
   │  "할 일 있어?" ──────────────────►│
   │                                   │  작업 없음
   │  "없어" ◄─────────────────────────│
   │                                   │
   │  ... 5초 후 ...                   │
   │                                   │
   │  "할 일 있어?" ──────────────────►│
   │                                   │  작업 생김!
   │  "응, 이거 해" ◄──────────────────│
```

**MQTT: 서버가 즉시 알려줌**
```
[단말]                    [Broker]                    [서버]
   │                          │                          │
   │  Subscribe               │                          │
   │  vehicle/VIN-0002/cmd    │                          │
   │ ────────────────────────►│                          │
   │                          │                          │
   │  (연결 유지 중...)        │                          │
   │                          │                          │
   │                          │     Publish              │
   │                          │     "OTA 시작해"          │
   │                          │◄─────────────────────────│
   │                          │                          │
   │  메시지 수신 (즉시!)      │                          │
   │◄─────────────────────────│                          │
```

## 3. RabbitMQ 상세 설명

### 3.1 RabbitMQ란?

- **역할**: 내부 서비스 간 메시지 브로커
- **프로토콜**: AMQP (Advanced Message Queuing Protocol)
- **특징**: 범용 메시지 큐, 다양한 라우팅 패턴 지원

### 3.2 핵심 개념

```
┌─────────────────────────────────────────────────────────────────┐
│                     RabbitMQ 구조                                │
├─────────────────────────────────────────────────────────────────┤
│                                                                 │
│   [Producer]                                                    │
│   (메시지 발행자)                                                │
│       │                                                         │
│       │  message                                                │
│       ▼                                                         │
│   ┌─────────────────────────────────────────────────────┐      │
│   │                    Exchange                          │      │
│   │  (메시지 라우터 - 어느 큐로 보낼지 결정)               │      │
│   └───────────────────────┬─────────────────────────────┘      │
│                           │                                     │
│            ┌──────────────┼──────────────┐                     │
│            │              │              │                      │
│            ▼              ▼              ▼                      │
│       ┌────────┐    ┌────────┐    ┌────────┐                   │
│       │ Queue  │    │ Queue  │    │ Queue  │                   │
│       │ VIN-01 │    │ VIN-02 │    │ VIN-03 │                   │
│       └────┬───┘    └────┬───┘    └────┬───┘                   │
│            │              │              │                      │
│            ▼              ▼              ▼                      │
│       [Consumer]    [Consumer]    [Consumer]                   │
│       (단말 워커)    (단말 워커)    (단말 워커)                   │
│                                                                 │
└─────────────────────────────────────────────────────────────────┘
```

### 3.3 Exchange 타입

| 타입 | 라우팅 방식 | 예시 |
|------|------------|------|
| **Direct** | Routing Key 정확히 일치 | `vin.VIN-0002` → VIN-0002 큐만 |
| **Fanout** | 모든 큐에 복사 | 전체 공지 |
| **Topic** | 패턴 매칭 | `vin.*` → 모든 VIN 큐 |
| **Headers** | 헤더 값 기반 | 잘 안 씀 |

### 3.4 이 프로젝트에서의 RabbitMQ 사용

```
[Vue 대시보드]
     │
     │ "VIN-0002에 업데이트 걸어줘"
     ▼
[Java SyncML Server]
     │
     ├─ 1. DB에 Job 저장 (status=QUEUED)
     │
     └─ 2. RabbitMQ에 발행
          Exchange: device.commands
          Routing Key: vin.VIN-0002
          Message: { "jobId": 101, "vin": "VIN-0002", "type": "FUMO_UPDATE" }
               │
               ▼
          ┌────────────────┐
          │ Queue: VIN-0002 │
          └───────┬────────┘
                  │
                  ▼
          [단말 시뮬레이터 VIN-0002]
          "아 나한테 작업 왔구나"
          "서버에 SyncML로 접속해야지"
```

**핵심**: RabbitMQ는 **"작업 왔다"는 알림**만 전달.  
실제 OTA 명령/상태 교환은 **SyncML로 별도 수행**.

## 4. Kafka 상세 설명

### 4.1 Kafka란?

- **역할**: 대용량 이벤트 스트리밍 플랫폼
- **개발**: LinkedIn → Apache 오픈소스
- **특징**: 고성능, 순서 보장, 로그 영구 저장

### 4.2 RabbitMQ vs Kafka 비교

| 항목 | RabbitMQ | Kafka |
|------|----------|-------|
| **설계 목적** | 범용 메시지 큐 | 이벤트 스트리밍/로그 |
| **메시지 보관** | 소비 후 삭제 | 영구 저장 (설정 기간) |
| **재처리** | 어려움 | 쉬움 (offset 이동) |
| **순서 보장** | 큐 단위 | 파티션 단위 |
| **처리량** | 수만 msg/sec | 수백만 msg/sec |
| **복잡도** | 낮음 | 높음 |
| **적합 용도** | 작업 분배, RPC | 로그 수집, 이벤트 소싱 |

### 4.3 Kafka 구조

```
┌─────────────────────────────────────────────────────────────────┐
│                       Kafka 구조                                 │
├─────────────────────────────────────────────────────────────────┤
│                                                                 │
│   [Producer]                                                    │
│       │                                                         │
│       │  이벤트 발행                                             │
│       ▼                                                         │
│   ┌─────────────────────────────────────────────────────┐      │
│   │                     Topic                            │      │
│   │   ┌───────────────────────────────────────────┐     │      │
│   │   │  Partition 0: [msg1][msg2][msg3][msg4]... │     │      │
│   │   ├───────────────────────────────────────────┤     │      │
│   │   │  Partition 1: [msg1][msg2][msg3]...       │     │      │
│   │   ├───────────────────────────────────────────┤     │      │
│   │   │  Partition 2: [msg1][msg2]...             │     │      │
│   │   └───────────────────────────────────────────┘     │      │
│   └─────────────────────────────────────────────────────┘      │
│                           │                                     │
│            ┌──────────────┼──────────────┐                     │
│            ▼              ▼              ▼                      │
│       [Consumer 1]   [Consumer 2]   [Consumer 3]               │
│       (Partition 0)  (Partition 1)  (Partition 2)              │
│                                                                 │
│   → 각 Consumer는 offset으로 어디까지 읽었는지 추적              │
│   → 과거 메시지 다시 읽기 가능                                   │
│                                                                 │
└─────────────────────────────────────────────────────────────────┘
```

### 4.4 Kafka 사용 예시 (OTA 시스템)

```
[이벤트 발생]
│
├─ Topic: ota-events
│    ├─ {"type":"JOB_CREATED", "vin":"VIN-0002", "jobId":101}
│    ├─ {"type":"DOWNLOAD_STARTED", "vin":"VIN-0002", "jobId":101}
│    ├─ {"type":"DOWNLOAD_COMPLETED", "vin":"VIN-0002", "jobId":101}
│    ├─ {"type":"INSTALL_STARTED", "vin":"VIN-0002", "jobId":101}
│    └─ {"type":"INSTALL_COMPLETED", "vin":"VIN-0002", "jobId":101}
│
├─ Consumer Group: analytics
│    └─ 통계/분석 서비스가 모든 이벤트 수집
│
├─ Consumer Group: notification
│    └─ 알림 서비스가 완료/실패 이벤트만 필터링
│
└─ Consumer Group: audit
     └─ 감사 로그 서비스가 전체 이벤트 영구 저장
```

### 4.5 이 프로젝트에서 Kafka가 필요한가?

| 상황 | 추천 |
|------|------|
| 단말 100대 미만 | RabbitMQ로 충분 |
| 단말 1000대+ | RabbitMQ 또는 Kafka |
| 모든 이벤트 로그 저장 필요 | Kafka |
| 실시간 분석/대시보드 | Kafka Streams |
| 단순 작업 분배 | RabbitMQ |

**이 프로젝트**: RabbitMQ로 충분. Kafka는 **"알고 있으면 좋다"** 수준.

## 5. 인증 패턴 비교

각 기술마다 인증 방식이 다르다. 본질적인 "신원 확인"은 같지만 프로토콜/환경에 따라 구현이 다름.

### 5.1 인증 방식 한눈에 비교

| 항목 | SyncML | MQTT | RabbitMQ | Kafka |
|------|--------|------|----------|-------|
| **인증 시점** | 매 세션 시작 | 연결(Connect) 시 | 연결(Connection) 시 | 연결 시 |
| **기본 방식** | Basic, MD5, HMAC | Username/Password | Username/Password | SASL |
| **Nonce 사용** | ✅ (Replay Attack 방지) | ❌ | ❌ | ❌ |
| **TLS/SSL** | 별도 설정 | ✅ 권장 | ✅ 권장 | ✅ 권장 |
| **토큰 기반** | ❌ | ✅ JWT 가능 | ✅ OAuth 2.0 | ✅ OAuth 2.0 |
| **인증 정보 위치** | `<Cred>` XML 요소 | CONNECT 패킷 | AMQP 프레임 | SASL 핸드셰이크 |

### 5.2 SyncML 인증 상세

SyncML은 **세션 기반** 인증으로, 매 세션마다 `<Cred>` 요소로 인증한다.

**지원 인증 타입:**

| 타입 | 형식 | 설명 |
|------|------|------|
| `syncml:auth-basic` | `Base64(username:password)` | 평문 인코딩 (TLS 필수) |
| `syncml:auth-md5` | `Base64(MD5(username:password:nonce))` | Nonce로 Replay Attack 방지 |
| `syncml:auth-hmac` | HMAC 서명 | 미구현 (고급) |

**Nonce 기반 MD5 인증 흐름:**

```
┌─────────────────────────────────────────────────────────────────┐
│                    SyncML Nonce 인증 흐름                        │
├─────────────────────────────────────────────────────────────────┤
│                                                                 │
│  [최초 접속]                                                     │
│  Client → Server: SyncML 요청 (Cred 없음)                        │
│  Server → Client: Status 401 + Chal(Nonce₁ 발급)                │
│  Server: Nonce₁을 DB에 저장                                      │
│                                                                 │
│  [인증 시도]                                                     │
│  Client: MD5(username:password:Nonce₁) 계산                     │
│  Client → Server: Cred에 Base64(해시값) 전송                     │
│                                                                 │
│  [성공 시]                                                       │
│  Server → Client: Status 212 + NextNonce(Nonce₂)                │
│  → Nonce₁ 폐기, Nonce₂로 교체 (다음 세션용)                      │
│                                                                 │
│  [실패 시]                                                       │
│  Server → Client: Status 401 + 동일 Nonce₁                      │
│  → fail_count 증가, 5회 초과 시 계정 잠금                        │
│                                                                 │
└─────────────────────────────────────────────────────────────────┘
```

**SyncML Cred XML 예시:**
```xml
<Cred>
  <Meta>
    <Type xmlns="syncml:metinf">syncml:auth-md5</Type>
    <Format>b64</Format>
  </Meta>
  <Data>dGhpc2lzYW1kNWhhc2g=</Data>  <!-- Base64(MD5(user:pass:nonce)) -->
</Cred>
```

**비밀번호 저장 구조:**
```
┌─────────────────┐                    ┌─────────────────┐
│   Client (단말) │                    │   Server (DB)   │
├─────────────────┤                    ├─────────────────┤
│ username        │  ◄── 동일 ──►      │ username        │
│ password (평문) │                    │ password_hash   │
│ nonce (서버발급)│  ◄── 동일 ──►      │ server_nonce    │
└─────────────────┘                    └─────────────────┘
※ 단말: 평문 비밀번호 보유 (해시 계산용)
※ 서버: 해시 저장 (Basic), 또는 별도 저장 (MD5)
```

### 5.3 MQTT 인증 상세

MQTT는 **연결 시점**에 한 번 인증하고, 이후 연결 유지.

**지원 인증 방식:**

| 방식 | 설명 | 보안 수준 |
|------|------|-----------|
| Username/Password | CONNECT 패킷에 포함 | 낮음 (TLS 필수) |
| TLS 클라이언트 인증서 | X.509 인증서 | 높음 |
| JWT 토큰 | Password 필드에 JWT | 중간~높음 |
| OAuth 2.0 | 외부 인증 서버 연동 | 높음 |

**MQTT 인증 흐름:**
```
┌────────────────────────────────────────────────────┐
│              MQTT 인증 흐름                         │
├────────────────────────────────────────────────────┤
│                                                    │
│  [Client]                    [MQTT Broker]         │
│     │                              │               │
│     │  CONNECT                     │               │
│     │  username: "device0001"      │               │
│     │  password: "password123"     │               │
│     │ ────────────────────────────►│               │
│     │                              │               │
│     │  CONNACK (Return Code 0)     │               │
│     │ ◄────────────────────────────│ (인증 성공)   │
│     │                              │               │
│     │  이후 Pub/Sub 자유롭게       │               │
│     │ ◄───────────────────────────►│               │
│                                                    │
└────────────────────────────────────────────────────┘
```

### 5.4 RabbitMQ 인증 상세

RabbitMQ는 **AMQP 연결 시점**에 인증.

**지원 인증 방식:**

| 방식 | 설명 | 설정 |
|------|------|------|
| **PLAIN** | Username + Password | 기본값 |
| **AMQPLAIN** | AMQP 전용 | 레거시 |
| **EXTERNAL** | TLS 클라이언트 인증서 | 고급 |
| **LDAP** | 외부 LDAP 서버 | 기업용 |
| **OAuth 2.0** | JWT 토큰 | 플러그인 필요 |

### 5.5 Kafka 인증 상세

Kafka는 **SASL(Simple Authentication and Security Layer)** 기반.

**지원 인증 방식:**

| 방식 | 설명 | 복잡도 |
|------|------|--------|
| **SASL/PLAIN** | Username + Password | 낮음 |
| **SASL/SCRAM** | Challenge-Response | 중간 |
| **SASL/GSSAPI** | Kerberos | 높음 (기업용) |
| **SASL/OAUTHBEARER** | OAuth 2.0 JWT | 중간 |
| **SSL/TLS** | 인증서 기반 | 높음 |

**Kafka 인증 설정 예시:**
```properties
# client.properties
security.protocol=SASL_SSL
sasl.mechanism=PLAIN
sasl.jaas.config=org.apache.kafka.common.security.plain.PlainLoginModule required \
  username="kafka-client" \
  password="secret";
```

### 5.7 면접 대비: 인증 관련

**Q: "SyncML과 MQTT의 인증 차이점은?"**

> SyncML은 매 세션마다 Cred 요소로 인증하고, Nonce를 사용해 Replay Attack을 방지합니다.
> MQTT는 연결 시점에 한 번 인증하고, 이후 연결을 유지합니다.
> SyncML은 상태 기반 Challenge-Response, MQTT는 연결 기반 인증입니다.

**Q: "Nonce가 뭐고 왜 쓰나요?"**

> Nonce는 서버가 발급하는 일회용 토큰입니다.
> 클라이언트가 비밀번호와 Nonce를 합쳐서 해시를 만들어 보냅니다.
> 같은 인증 정보를 재사용해도 Nonce가 바뀌면 해시가 달라지므로,
> Replay Attack(재전송 공격)을 방지할 수 있습니다.

## 7. 면접 대비 요약

### Q: "MQTT, RabbitMQ, Kafka의 공통점과 차이점은?"

> 본질적으로 셋 다 같습니다. "Consumer에게 메시지를 전달"하는 것입니다.
> 차이는 환경과 부가기능입니다.
> - MQTT: 외부 IoT 최적화, 경량 프로토콜
> - RabbitMQ: 내부 서비스 간 작업 분배, 소비 후 삭제
> - Kafka: 대용량 처리, 메시지 영구 저장, 재처리 가능
> 
> 비유하면 MQTT는 퀵서비스, RabbitMQ는 일반 택배, Kafka는 대형 물류창고입니다.

### Q: "SyncML과 MQTT의 차이점은?"

> SyncML은 XML 기반 OMA 표준 프로토콜로, 단말이 먼저 접속하는 Polling 구조입니다.
> MQTT는 경량 Pub/Sub 프로토콜로, 브로커를 통해 서버가 단말에 즉시 Push 가능합니다.
> SyncML은 표준 준수가 필요한 환경에서, MQTT는 신규 IoT 프로젝트에서 주로 사용됩니다.

### Q: "RabbitMQ와 Kafka의 차이점은?"

> RabbitMQ는 범용 메시지 큐로, 작업 분배와 즉시 처리에 적합합니다. 메시지는 소비 후 삭제됩니다.
> Kafka는 이벤트 스트리밍 플랫폼으로, 대용량 로그 수집과 재처리에 적합합니다. 메시지가 영구 저장됩니다.
> 단순 작업 분배는 RabbitMQ, 이벤트 소싱이나 분석이 필요하면 Kafka를 선택합니다.

### Q: "이 프로젝트에서 RabbitMQ를 어떻게 사용했나요?"

> 외부 단말 통신은 SyncML로, 내부 작업 분배는 RabbitMQ로 분리했습니다.
> 대시보드에서 업데이트 요청 시 RabbitMQ에 "작업 생성" 이벤트를 발행하고,
> 해당 VIN의 단말 시뮬레이터가 이를 소비하여 SyncML 세션을 시작합니다.
> RabbitMQ는 SyncML 메시지를 직접 처리하지 않고, "알림"만 전달합니다.
